# 2.0 Agent Control Plane: Authorization, Approval, Audit

Status: IN PROGRESS - MCP Stages 1-3 are shipped for tool dispatch
(independent of 1.x quality work; unblocks unattended/enterprise consumption).
ROADMAP anchors: Active Queue #21; SECURITY.md threat T8; cost-cap policy
(`mcp_server/cost_caps.py`, v1.30.0); write guard (#11, shipped).

## Motivation

Today MCP has per-tool scopes, server-issued approval tokens, a structured
invocation audit trail, and runtime budget propagation for fast optional stages
and non-fast optional strategy documents. The remaining gaps are A2A parity,
output-consumption resources, and better visibility around required provider
tasks that expose no live cost state. The shape of the work is narrow by
design: harden the control plane for primr's actual surface, not build generic
agent middleware.

## Immediate next slice

The next control-plane slice is job-scoped artifact consumption plus A2A parity.
MCP already has scopes, approval tokens, structured audit, and runtime budget
propagation for the shipped paths. The remaining safety gap is that clients
still need a clean way to consume compact artifacts without broad filesystem
access or full-report context dumps. Add scoped resources for summaries,
sources, trace metadata, and usage/cost records, then apply the same scope,
approval, and audit semantics to A2A.

## Design: three stages, each building on the previous

### Stage 1 - per-tool, capability-scoped authorization (T8)

Status: SHIPPED for MCP tool dispatch.

- The JWT `role` claim already exists and maps to scopes; enforce it per
  tool. Scope vocabulary stays small and capability-shaped:
  `read` (estimates, status, resources, qa), `research` (research_company,
  generate_strategy, skill packs), `delegate` (delegate_to_agent),
  `admin` (job clearing)
- Tool registry annotates each tool with its required scope; the central
  `call_tool` dispatcher checks before handler dispatch (one seam - same
  pattern as the cost-cap check)
- Default deny for unknown tools/scopes; stdio (host-mediated) keeps current
  behavior unless scopes are configured - mirrors the cost-cap
  transport-default precedent
- A2A co-host inherits the same check at its tool boundary

### Stage 2 - server-issued approval tokens for cost-incurring operations

Status: SHIPPED for MCP cost-cap-governed execution tools:
`research_company`, `generate_strategy`, and `generate_skill_pack`.

- Flow: `estimate_run` (or `estimate_skill_pack`) returns, alongside the
  estimate, a short-lived single-use `approval_token` bound to
  {tool, args-hash, max-cost, expiry}
- Cost-incurring tools accept the token; with enforcement on, a valid token
  is required *in addition to* the cap, and the args-hash binding stops
  approve-A-execute-B swaps
- Tokens are HMAC-signed with a server secret (no storage needed beyond a
  replay set with TTL); single-use enforced before execution starts
- The packaged OpenClaw workflows and the Claude skill adopt the flow so the
  estimate-first pattern becomes cryptographically checkable, not just
  documented

### Stage 3 - structured invocation audit log

Status: SHIPPED for MCP tool calls.

- Append-only JSONL:
  timestamp, transport, tool name, hashed caller id, granted scopes, args hash
  and result hash (never raw args or raw results), approval token id,
  estimated/max cost, job id, duration, and outcome
- `primr://agent/audit/recent` exposes recent events to local stdio callers
  and admin-scoped HTTP callers
- The fields already designed for App Insights (#22: request_id, job_id,
  tool_name, duration_ms) reuse this record; OTel spans carry the ids
- Future CLI rendering and OTLP export can read this same JSONL surface without
  changing the tool dispatcher

### Runtime budget propagation

Status: SHIPPED for MCP `research_company` fast-path runs and non-fast
optional strategy documents.

- `research_company` passes the approved `max_estimated_cost_usd` into
  `PipelineRunner` after the cost cap and approval token checks succeed
- `PipelineRunner` activates `utils.run_budget.RunBudget`, so optional-spend
  checkpoints behave the same way as CLI `--budget`
- The process-global budget is cleared in a `finally` to avoid leaking state
  into later jobs in the long-lived MCP server process
- `estimate_run` and CLI `--dry-run --json` expose the same
  `budget_enforcement` payload, so agent clients can distinguish fast optional
  checkpoints, non-fast optional strategy checkpoints, and estimate-gated-only
  modes before asking for approval
- Remaining: scrape is still estimate-gated only, and required Deep Research
  tasks cannot be stopped mid-flight because the provider exposes cost at task
  completion rather than at live checkpoints

## Order of operations

Stage 1 -> 2 -> 3 strictly (2 needs 1's identity enforcement to mean
anything; 3 logs what 1+2 decided). Runtime budget propagation follows those
stages because it depends on an approved cap being meaningful. Each stage is
independently shippable and useful. Remaining work extends the same controls to
A2A, output resources, and better post-hoc visibility for non-interruptible
provider tasks.

## Validation cost

Entirely free: all three stages are deterministic and fully testable with
the existing JWT/test-server harnesses (165 a2a + mcp_server suites).
Red-team style tests to pin: scope escalation attempts, token replay, token
args-swap, audit-log injection via crafted company names.

## Exit criteria

- A low-trust agent can hold an `read`-only credential that cannot start
  paid work; a `research` credential cannot delegate
- A cost-incurring call without a valid, matching approval token is refused
  when enforcement is on (HTTP default-on, consistent with cost caps)
- Every tool invocation appears in the audit log with identity, cost, and
  outcome; the log survives crashes uncorrupted

## Explicitly not

- No user database, no OAuth server, no session management - identity stays
  JWT-claims-in, decisions-out
- No generic policy engine (OPA etc.); the scope table is a dict in code
- No multi-tenant isolation guarantees beyond per-credential scoping -
  primr remains a single-operator tool whose *callers* may be many agents
