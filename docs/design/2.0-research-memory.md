# 2.0 Research Memory: Compounding Across Runs

Status: IN PROGRESS - third 2.0 pillar in build order. Layer 1 storage,
company track/list/show profiles, and profile-plus-hypotheses export are
shipped; clear and run-history wiring remain planned.
ROADMAP anchors: "Cross-Run Research Memory", "Strategy Delta Mode",
"Watch / Delta as a Consumed Primitive" (Considered for Later); per-user
cache (#12, shipped v1.30.0).

## Motivation

Each run starts cold. Researching 50 companies in one industry rediscovers
the same context 50 times; re-running a tracked company regenerates what
hasn't changed. Memory turns runs into a compounding asset - and it is the
pillar that makes primr valuable inside *other people's loops*, where the
same targets recur.

## Immediate next slice

Memory is deliberately after label calibration and job-scoped artifact
resources. Prior-run claims should not be able to re-enter a new report as
fresh findings unless their provenance and confidence are explicit. The first
build slice is therefore layer 1 only: filesystem-backed company tracking in
the per-user data directory, run pointers, hypothesis history, freshness
metadata, OKF export, deletion, retention docs, and no-secret write checks.

## Design: three layers, built strictly in order

### Layer 1 - persistent company tracking (filesystem, no new deps)

Shipped foundation:

- `ResearchMemory()` now defaults to `<per-user data dir>/research_memory`
  instead of a project-local or logs folder. `PRIMR_DATA_DIR` relocates that
  durable state.
- Memory writes reject secret-like values before YAML is written, reusing the
  same masking patterns used by persistent logs.
- `primr doctor` File Locations reports both the user data root and research
  memory path.
- `primr company track <name> <url>` creates or updates a local JSON profile
  under `<per-user data dir>/company_profiles`, rejects URL userinfo and
  secret-like values, and records retention/classification metadata plus an
  empty run-pointer list for later pipeline wiring.
- `primr company list` and `primr company show <name>` provide deterministic
  local inventory/readback without paid calls or network access.
- `primr company export <name>` writes a local JSON + Markdown bundle under
  the profile's `exports/` folder. It includes profile metadata, persisted
  research-memory hypotheses with confidence tags, and explicit flagged gaps
  for missing run-history and claim-store data.
  The bundle shape is OKF (markdown + YAML frontmatter + linked tree; see
  [open-knowledge-format.md](open-knowledge-format.md)); the current layer 1
  export is the shallow profile/hypothesis foundation and deliberately does not
  pretend to be the full claim graph until layer 2 lands.
- Research memory (`agentic.memory.ResearchMemory`) already tracks
  hypotheses; layer 1 gives it a stable per-company home and CLI surface

### Layer 2 - claim store + priming

- SQLite (stdlib, no new service): claims with company, section, text,
  confidence label, citations, timestamp, embedding. A claim with its
  confidence label, citations, and links *is* one OKF file, so the store's
  portable/export form is an OKF bundle (round-trip lossless); see
  [open-knowledge-format.md](open-knowledge-format.md)
- Embeddings: local sentence-transformers when available, Gemini embedding
  API otherwise - chosen per the backend-freedom profile
- `primr memory search "<query>"`, `primr memory timeline "<Company>"`
- Priming: at run start, query for related companies/industry claims and
  inject as *clearly-provenance-marked* context into the analysis stage
  (fenced as data; prior-run claims are never silently re-asserted as fresh
  findings - they enter as "prior research suggests, validate:" items)

### Layer 3 - Strategy Delta Mode

- Given a prior run's artifacts + claim store, gather fresh signals (recon,
  hiring, external), diff against the stored claims, regenerate only sections
  whose evidence materially changed, and emit a "what changed since <date>"
  delta artifact alongside the refreshed report
- Stays inside the single-job model: a delta run is one job, not a daemon.
  The watch/poll loop that *triggers* delta runs lives on the consumer side
  (ROADMAP: "Watch / Delta as a Consumed Primitive")
- Change detection trusts labels - which is why 1.x label calibration is a
  soft prerequisite: a delta gated on uncalibrated claims propagates noise

## Data governance (ships WITH layer 1, not later)

Memory creates a new surface the existing threat model doesn't cover:

- **Locality:** all stores under the per-user data dir; nothing leaves the
  machine except via explicit `export`
- **Deletion:** `primr memory clear [--company X]` removes claims + profile;
  documented retention default (keep until cleared)
- **Classification:** profile folders are operator data about third parties -
  the docs say so plainly, and `doctor` File Locations lists the store
- **No secrets in memory entries** (existing rule, enforced at the write
  seam with the same scanner used for research memory)

## Validation cost

Layers 1-2 are fully free to validate (deterministic + property tests on the
store; priming tested with mocked LLM). Layer 3 needs one tracked-company
re-run to validate end-to-end (~$1 standard run + delta run at a fraction).

## Exit criteria

- A tracked company's second run primes from the first and emits a delta
  artifact; the claim store answers cross-company queries; clear/export work
  as documented; the governance page exists
- Invariant pinned by tests: priming may *inform* analysis but a prior-run
  claim can never appear in a new report without fresh attribution

## Explicitly not

- No daemon, no scheduler, no push notifications - consumers poll/trigger
- No cloud sync of memory; export is the only egress
- No cross-user/multi-tenant store (single-operator tool)
